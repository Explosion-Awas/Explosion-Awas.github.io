这个站做得比较朴素。把一堆 Markdown 丢进去，大约一千二百行 Python 把它变成静态 HTML，剩下的交给 GitHub Pages。没有数据库，没有前端路由，运行时也不会请求任何第三方。它应该在网速很快的时候、在限制重重的网络里、以及十年以后，看起来都一样。

站内还跑着两种语言。英文在根目录，中文在 `/zh/`，构建时分别读 `content/` 下平行的两个文件夹。页头的开关会指向对应的那一页，而不是首页，所以两个版本必须同步。整套东西里，只有这一部分需要靠自觉，而不是靠代码。

## 流程

```bash
python build.py            # 构建到 public/
python build.py --serve    # 本地预览，存盘自动重建
python build.py --check    # 检查所有站内链接
```

生成器只有一个文件，依赖也是两个，`markdown` 和 `pygments`，其余都是标准库。内容按语言读进来，渲染之后在两套路径前缀下各写一遍；feed、搜索索引和 sitemap 也跟着分成两份。

## 字体和公式都自己托管

第三方字体和脚本 CDN，是同一个页面在不同人那里长得不一样的最常见原因。所以这些东西全在仓库里：正文用的 `woff2` 文件，以及数学公式用的 KaTeX。

只有真的出现公式的页面才会加载 KaTeX。构建过程知道这件事，因为它在写 HTML 之前就已经看过公式了。

<div class="callout">
<p><strong>渲染检查</strong>行间公式必须原样穿过 Markdown 管线：下标、分式、极限，一个都不能少。下面这个恒等式是标准结果，放在这里只为了证明这条路是通的。</p>

$$
\int_{-\infty}^{\infty} e^{-a x^{2} + b x}\,dx \;=\; \sqrt{\frac{\pi}{a}}\; \exp\!\left(\frac{b^{2}}{4a}\right),
\qquad a > 0
$$

</div>

行内公式也得能用，比如 $e^{i\omega T}$ 和 $\varepsilon \in (0,\,1]$，而且下划线不能变成斜体。构建时会把公式先藏起来，等 Markdown 处理完再放回去，`w*y*y/2 >= 5` 这种行内代码同样安全。

## 代码在构建时就高亮好了

不需要 highlight.js，不需要 shiki，运行时零成本：

```python
def reading_time(words: int, wpm: int = 210) -> int:
    """Minutes, rounded up, with a floor of one."""
    return max(1, round(words / wpm))
```

这就是生成器里真的在用的函数。Pygments 输出 token 的 span，样式表把它们映射到和页面一致的配色上，所以亮色和暗色主题始终同步。

## 一个页面要付多少

这些数字是从文件本身量出来的，不是估的：

| 资源 | 大小 | 加载于 |
| --- | --- | --- |
| HTML | 12–19 KB | 每个页面 |
| 样式表 | 62 KB | 每个页面 |
| 字体（7 个 woff2） | 231 KB | 每个页面，会缓存 |
| KaTeX CSS + JS | 294 KB | 只有带公式的页面 |
| JavaScript | 10 KB | 每个页面 |

所以一篇普通文章首次访问大约 320 KB，字体也算进去了，再访问一次就是零。带公式的页面再多付 294 KB，大部分是排版引擎本身，浏览器在第一次看到公式后就会把它缓存下来。

## 取舍

静态生成意味着没有评论、没有服务端搜索，也没法在手机上随手发一篇而不等构建。搜索索引是一个按需拉取的 JSON 文件，每种语言一份，对这个体量的手记来说够用。如果哪天不够用了，那是另一个问题。

构建过程不判断内容对不对、有没有验证过，也不管是谁写的，它只负责把文件变成网页。[^katex]

[^katex]: KaTeX 固定在 `theme/katex/` 里的那个版本，所以上游发新版也不会改变一篇旧文章的渲染结果。
